## ~~1. 产品目标~~（已取消）

MediaHub 后续从“播放器”扩展为一个下载与播放一体的桌面软件，顶层分成下载和
播放两部分：

```text
MediaHub
|-- 下载
|   |-- 音频下载
|   `-- 视频下载
`-- 播放
    |-- 本地播放
    `-- 直播播放
```

- 本地播放继续复用现有播放列表、歌词、波形、音量、倍速、进度和全屏能力。
- 直播播放继续执行 `v0.2直播播放.md` 与 `直播频道库与M3U开发规划.md`。
- 音频和视频下载完成后，可以“立即播放”或“加入本地播放列表”。
- 下载与播放是两个业务模块，下载失败不得影响正在播放的本地媒体或直播。

MediaHub 只处理用户有权下载和播放的内容。程序不绕过登录、付费、DRM、签名或
其他访问限制，也不承诺第三方站点接口长期可用。

## ~~2. 两个参考项目的实际评估~~（历史记录）

2026-08-05 对本机两个上游仓库做了只读审查，没有安装依赖、访问站点或执行其中
脚本。

| 项目 | 审查版本 | 主要入口 | 规模与测试 | 许可证 |
|---|---|---|---|---|
| `musicdl` | 2.13.4，提交 `d638fe8` | `MusicClient.search`、`parseplaylist`、`download` | 约 111 个 Python 文件，未发现单元测试 | PolyForm Noncommercial 1.0.0 |
| `videodl` | `videofetch` 0.9.1，提交 `1a93ac1` | `VideoClient.parsefromurl`、`download` | 约 146 个 Python 文件，未发现单元测试 | PolyForm Noncommercial 1.0.0 |

两个仓库都使用 Python，通过大量站点适配器解析元数据和临时下载地址。它们的
数据对象值得参考：

- `SongInfo` 包含来源、歌名、歌手、专辑、时长、码率、歌词、封面、格式和保存路径。
- `VideoInfo` 包含来源、标题、封面、音视频地址、格式、保存路径和外部下载器配置。
- 解析与下载基本分开，站点客户端通过注册表构建，视频客户端采用延迟实例化。

这些思路适合转化为 MediaHub 自己的纯业务模型，但不能直接把上游对象暴露给 GUI。
`raw_data`、下载头、Cookie、临时 URL 和代理配置可能含敏感信息，必须留在后端边界内。

## ~~3. 能否直接使用~~（历史记录）

### ~~3.1 许可结论~~（历史记录）

用户已明确 MediaHub 只供个人自用，不盈利、不商业分发。`musicdl` 与 `videodl`
采用的 PolyForm Noncommercial 1.0.0 允许个人使用、私人娱乐和业余项目，因此可以
把两个项目的固定版本直接用于 MediaHub 下载模块，不需要只参考后重新实现。

直接使用时仍需：

1. 保留两个项目的上游 `LICENSE`、版本、提交号和来源记录。
2. 不把包含上游代码的版本用于盈利或商业服务，也不公开分发当前自用整合包。
3. 如果以后改为公开分发、收费或商业使用，必须在变更用途前重新审查许可证。
4. 只下载用户有权获取的内容；代码许可证不替代内容版权和站点使用条款。

### ~~3.2 为什么仍不把 Python 仓库塞进 C++ 主进程~~（历史记录）

1. **运行时差异**：MediaHub 是 C++20/Qt，两个下载器是 Python。当前本机 Python
   3.14.4 未安装这两个包，而 videodl 的上游检查工作流使用 Python 3.10；其大量
   二进制依赖是否支持 3.14 未经验证。
2. **依赖过重**：依赖包含加密库、浏览器自动化、Node、FFmpeg、N_m3u8DL-RE、
   aria2、Bento4、Whisper、代理和 HLS 工具，不能全部塞进播放器发布包。
3. **缺少机器协议**：现有 CLI 面向终端交互，输出 Rich 进度条，没有稳定的 JSON
   协议、版本握手或适合 Qt 的取消语义。
4. **线程和取消不可控**：下载函数内部创建线程池并使用阻塞请求，部分路径调用
   `subprocess.run`。主程序不能可靠地暂停或取消单个任务，也不能保证子进程退出。
5. **文件安全不足**：下载过程直接写最终文件，缺少统一 `.part`、原子完成、磁盘
   空间检查和崩溃恢复规则。
6. **网络安全边界不同**：多个请求路径会在证书验证失败后以 `verify=False` 重试；
   MediaHub 不允许自动关闭 TLS 验证。
7. **功能越界**：仓库包含 Widevine/WVD、登录 Cookie、代理、通用解析站和 DRM
   相关路径，均不进入 MediaHub。
8. **维护成本高**：站点接口经常变化，上游仓库也明确依赖第三方在线解析服务；
   MediaHub 不能把所有站点“当前能用”当作产品承诺。

### ~~3.3 方案比较与结论~~（历史记录）

| 方案 | 优点 | 主要问题 | 决策 |
|---|---|---|---|
| 把两个仓库复制到 `Third_Party` | 上手最快 | 许可证、体积、Python、DRM 和维护风险全部进入主仓库 | 不采用 |
| 在 MediaHub 内嵌 CPython | 可以直接调用对象 API | ABI、GIL、依赖部署、崩溃隔离和升级复杂 | 不采用 |
| 直接启动现有 CLI | 改动少 | 终端交互、输出不稳定、无法可靠选项和取消 | 不采用 |
| 独立 Python worker | 直接调用两个项目的 API，同时隔离依赖和故障 | 需要自定义协议和进程树管理 | 正式采用 |
| MediaHub 自建直链下载后端 | 可测试、取消和文件安全可控 | 不会自动解析所有站点 | 作为基础能力采用 |

最终采用“两层后端”：MediaHub 自己的安全直链后端提供可控的基础能力；独立
Python worker 直接导入并调用 `musicdl`/`videodl` 的对象 API，提供音频搜索和视频
页面解析能力。worker 是 MediaHub 下载模块的正式后端，但不是启动和播放的必需
依赖；下载器崩溃、卡死或升级不得拖死播放器。

worker 使用独立 Python 3.10 或 3.11 环境，固定 `musicdl` 2.13.4 和
`videofetch` 0.9.1 及其提交。两个项目顶层会导入大量来源模块，实施时先验证完整
依赖能否稳定安装；随后在保留许可证的 MediaHub 私有副本中改为按允许来源延迟
导入，避免无关 CDM/WVD、浏览器自动化和解析站模块随启动加载。

## ~~7. 第一方直链下载后端~~（已取消）

先支持用户自己提供的 `http`/`https` 直接文件地址：

1. 只允许经过校验的 HTTP(S) URL，不接受 `file:`、脚本协议或任意命令。
2. 使用 Qt 网络栈异步请求，不阻塞 GUI。
3. TLS 验证失败即失败，绝不以关闭验证的方式重试。
4. 限制重定向次数，跨主机重定向时重新检查协议。
5. 下载到 MediaHub 自己创建的 `.part`，成功关闭并校验后再原子改为最终文件名。
6. 取消时停止网络请求并清理本任务的临时文件，不删除既有目标文件。
7. 目标文件已存在时让用户选择重命名、跳过或确认覆盖。
8. 下载前检查目标目录、可用空间和文件名；响应大小未知时持续检查写入错误。
9. 完成后按文件签名和扩展名做基本校验，再允许交给本地播放器。

断点续传、限速、并发数持久化和下载历史不进入最小增量，等基本安全链路稳定后再加。

## ~~8. Python worker 与上游直接整合~~（已取消）

许可决策已经通过。worker 直接调用固定版本上游 API，并与 MediaHub 使用版本化
JSON Lines 协议：

```json
{"version":1,"type":"resolve","request_id":"...","kind":"audio","query":"..."}
{"version":1,"type":"candidate","request_id":"...","candidate":{"id":"..."}}
{"version":1,"type":"progress","job_id":"...","downloaded":1024,"total":4096}
{"version":1,"type":"completed","job_id":"...","output_name":"example.mp3"}
```

协议规则：

- `stdout` 只允许一行一个 JSON 消息，Rich 输出和诊断转到经过脱敏的 `stderr`。
- 所有消息有版本、类型、请求/任务 ID 和大小上限；未知字段可忽略，未知类型拒绝。
- Qt 使用参数数组启动进程，不拼接 Shell 命令。
- URL、Cookie、请求头、代理、`raw_data` 和本机绝对路径不得跨边界返回。
- 解析结果在 worker 内以不透明 ID 保存，主程序只看到显示所需字段。
- 每个下载任务使用可独立终止的 worker 或受 Windows Job Object 管理的进程树；
  取消必须同时终止 worker、FFmpeg/Node 等子进程并清理本任务临时文件。
- worker 无响应、协议损坏、退出码异常或超时只让当前任务失败，不影响播放模块。
- 固定上游版本或提交；升级先跑契约测试和人工站点冒烟，不自动跟随最新版本。

第一轮适配仅选择不需要登录、Cookie、代理、DRM 或第三方“万能解析站”的少量来源。
Widevine、WVD、`pywidevine`、VIP Cookie、签名绕过和 `verify=False` 路径必须从能力表
中排除，不能只靠“不在界面显示”来隐藏。

## ~~9. 文件、配置和隐私~~（已取消）

- 默认下载目录使用 `QStandardPaths::DownloadLocation` 下的 MediaHub 子目录，允许
  用户选择其他目录；源码和安装目录不保存下载内容。

- “清理临时文件”只作用于带 MediaHub 任务标识且位于缓存根内的精确路径。
- 当前版本“播放器不修改用户媒体文件”的承诺保持不变；下载版本只向用户确认的
  输出目录创建新文件，不修改用户已有媒体。

# MediaHub 后续版本路线

> 状态：v0.2 进行中。用户已于 2026-08-05 明确启动开发。
>
> 分类：规划。
> 本文档说明 v0.2 直播播放和 v0.3 自研播放内核的主题、范围边界与已知难点。
> v0.2 的增量拆分与当前验收项见 `v0.2直播播放.md`。

## 1. 为什么先写这份文档

“输入 URL 就能看直播”和“自己写解码内核”是这个项目最初的两个动机。把它们放到
后续版本，不是放弃，而是为了让第一版有一个能够独立验收的完整形态。

提前记录范围有两个作用：

1. 开发 v0.1 时知道哪些设计要为后续留出空间，哪些不必提前抽象。
2. 遇到“顺手加一下”的诱惑时，有明确依据拒绝。

## 2. v0.1 需要为后续预留的空间

只预留以下三点，不做更多提前设计：

| 预留项 | 原因 |
|---|---|
| 媒体项区分“本地文件”和“网络流”两种来源类型 | v0.2 需要按来源类型改变超时和缓冲策略 |
| 播放状态包含“缓冲中” | 本地播放几乎用不到，但状态机提前留位比后期改枚举便宜 |
| `PlayerEngine` 是纯虚接口，GUI 不链接 libVLC | v0.3 替换内核的唯一前提 |

除此之外，v0.1 不为直播和自研内核编写任何代码，也不预留配置项和空函数。

## 3. v0.2：URL 直播播放

### 3.1 版本目标

在保留本地播放能力的基础上，用户可以输入一个直播地址并直接观看。

### 3.2 计划包含

- 地址输入栏与“打开网络地址”菜单。
- 地址合法性的基本检查与来源类型识别。
- 支持 libVLC 能够处理的常见直播协议。
- 缓冲状态显示与缓冲进度。
- 打开超时与用户可中断的连接过程。
- 直播失败提示和用户主动刷新；不自动判断卡顿或重连。
- 直播与点播的界面差异处理：直播不显示总时长，禁用进度拖动。
- 最近播放地址的会话内记录。
- 网络失败原因的可读提示。

### 3.3 计划不包含

- 直播源搜索、频道列表和内置源库。
- 需要登录、鉴权、签名或特定客户端标识的私有源。
- 录制、缓存到本地和回看。
- 弹幕、聊天和互动功能。
- 多路同时播放和画中画。
- 自适应码率的手动切换界面。
- 任何绕过访问限制或版权保护的能力。

### 3.4 已知难点

| 难点 | 说明 |
|---|---|
| 打开过程可能长时间无响应 | 必须异步打开并允许用户取消，不能阻塞主线程 |
| 直播没有总时长 | 状态机和界面都要能处理“时长未知”，不能假设时长总是有效 |
| 断流与网络抖动 | 协议行为差异导致自动判断不可靠，最终由用户通过按钮或 `F5` 主动刷新 |
| 地址有效性无法预先判断 | 只做基本格式检查，真正的可用性只能由打开结果决定 |
| 内核参数需要针对网络调整 | 缓存时长、超时等参数集中管理，不散落在业务代码里 |

### 3.5 合规边界

MediaHub 只负责播放用户自己提供的地址。项目不内置任何直播源列表，不提供源
搜索能力，也不实现任何绕过访问控制的手段。用户需要自行确保其播放的内容来源
合法。这一条写入 README，不因为实现方便而放宽。

## 4. v0.3：自研 FFmpeg 播放内核

### 4.1 版本目标

用 FFmpeg 从头实现一个 `PlayerEngine`，与现有 libVLC 实现并存，可以在两者之间
切换，用于对照验证和学习。

这个版本的首要产出是理解，不是性能。

### 4.2 计划包含

- FFmpeg 依赖接入与部署方案。
- 解封装：打开媒体、读取流信息、按流分发数据包。
- 音频解码与重采样，通过 Qt 音频输出播放。
- 视频解码与像素格式转换。
- 视频渲染：使用 OpenGL 控件显示解码后的帧。
- 音视频同步：以音频时钟为基准对齐视频显示时间。
- 定位：关键帧定位与解码器缓冲清理。
- 线程模型：解封装线程、音频解码线程、视频解码线程与队列。
- 内核切换开关，两套实现通过同一组测试。

### 4.3 计划不包含

- 硬件加速解码。
- 超越 libVLC 的格式覆盖率。
- 滤镜、变速和后处理。
- 替换 libVLC 实现。两套内核并存，libVLC 仍是默认。

### 4.4 已知难点

按预期难度排序：

1. **音视频同步**。这是自研播放器最核心也最容易做坏的部分。需要理解时间基、
   显示时间戳、时钟基准的选择，以及丢帧和等待的处理策略。
2. **定位后的状态恢复**。定位需要清空队列、刷新解码器缓冲并重建时钟，任何一步
   遗漏都会导致画面错乱或音画错位。
3. **线程与队列的生命周期**。多个线程共享有界队列，停止和释放时必须让所有线程
   确定性退出，不能依赖强制终止。
4. **像素格式与渲染**。解码输出的格式不固定，转换和上传纹理的开销需要控制。
5. **内存管理**。FFmpeg 是 C 库，每个分配都需要对应的释放，必须用 RAII 包装。

### 4.5 验证方式

v0.3 的核心验证手段是“同一组测试跑两套内核”：

- v0.1 和 v0.2 建立的状态机、播放列表和控制器测试完全复用。
- 新增内核只需要通过同样的集成测试，不为它单独放宽标准。
- 自研内核和 libVLC 内核播放同一文件，对比时长、定位结果和结束行为。

如果自研内核无法通过既有测试，说明抽象接口设计有问题或实现有缺陷，两者都需要
在文档层面先解决。

## 5. 更后续的候选

以下能力目前没有版本归属，只作为候选记录：

- 字幕加载与显示。
- 多音轨与多视频轨切换。
- 倍速播放与逐帧步进。
- 视频截图。
- 媒体库、目录扫描与播放历史。
- 音效处理与均衡器。
- 快捷键自定义与配置持久化。
- Qt 6 升级。
- 硬件加速解码。

任何一项要开发时，先建立新的版本规划文档，再拆阶段，不直接开始编码。

## 6. 版本号约定

- v0.1.0：本地播放，libVLC 内核。
- v0.2.0：增加 URL 直播。
- v0.3.0：增加自研 FFmpeg 内核。

每个版本都是功能增量，不是架构重写，因此主版本号保持 `0`。只有在确定 API 稳定
并对外发布时才考虑 `1.0.0`。

## 2. 核心类型

### 2.1 媒体项

表达一个可播放对象。第一版只会出现本地文件，但来源类型枚举提前保留网络流，
理由见 [后续版本路线.md](../规划/后续版本路线.md) 第 2 节。

```text
MediaSourceKind : LocalFile | NetworkStream

MediaItem
├── source        来源字符串，本地路径或 URL，UTF-8
├── kind          来源类型
└── displayName   界面显示名称，本地文件默认取文件名
```

值语义，可拷贝。判断来源类型的规则集中在一个函数中，不散落在界面代码里。

### 2.2 播放状态

```text
PlaybackState : Idle | Opening | Buffering | Playing
              | Paused | Stopped | Ended | Failed
```

状态含义见 [第一版MVP.md](../规划/第一版MVP.md) 第 5 节。

`Buffering` 在本地播放中几乎不出现，但提前保留，避免 v0.2 修改枚举。

阶段 3 固定以下转换表。`是` 表示允许状态事件，`同` 表示重复事件被接受但状态不变，
`否` 表示拒绝且保留原状态：

| 从／到 | Idle | Opening | Buffering | Playing | Paused | Stopped | Ended | Failed |
|---|---|---|---|---|---|---|---|---|
| Idle | 同 | 是 | 否 | 否 | 否 | 否 | 否 | 是 |
| Opening | 否 | 同 | 是 | 是 | 是 | 是 | 是 | 是 |
| Buffering | 否 | 是 | 同 | 是 | 是 | 是 | 是 | 是 |
| Playing | 否 | 是 | 是 | 同 | 是 | 是 | 是 | 是 |
| Paused | 否 | 是 | 是 | 是 | 同 | 是 | 是 | 是 |
| Stopped | 否 | 是 | 是 | 是 | 否 | 同 | 否 | 是 |
| Ended | 否 | 是 | 是 | 是 | 否 | 是 | 同 | 是 |
| Failed | 否 | 是 | 否 | 否 | 否 | 是 | 否 | 同 |

从活动状态回到 `Opening` 表示切换媒体；`Failed` 可通过重新打开或停止恢复。解除当前
媒体不伪装成内核事件，而是显式调用 `reset()` 回到 `Idle`。状态机用
`Changed`、`Unchanged` 和 `Rejected` 区分这三类结果。

### 2.3 播放位置

```text
PlaybackPosition
├── current    std::chrono::milliseconds
├── total      std::optional<std::chrono::milliseconds>
└── seekable   bool
```

`total` 使用 `optional` 而不是用 `0` 或 `-1` 表达“未知”。直播没有总时长，第一版
虽然用不到，但类型设计必须诚实。

### 2.4 播放失败

```text
PlaybackErrorKind : SourceNotFound | SourceUnreadable
                  | UnsupportedFormat | AudioDeviceUnavailable
                  | EngineNotInitialized | Unknown

PlaybackError
├── kind          失败类别
├── engineDetail  内核给出的原始信息，用于日志和排查
└── userMessage   面向用户的中文完整句子
```

界面只显示 `userMessage`。`engineDetail` 只进日志，不直接展示给用户。

### 2.5 播放模式

```text
PlaybackMode : Sequential | LoopAll | LoopOne
```

## 3. PlayerEngine 抽象接口

### 3.1 设计约束

已在 [播放内核选型.md](播放内核选型.md) 第 4 节确定，这里重申最关键的一条：

> **所有操作都是请求，不保证同步完成。真正的结果通过事件回传。**

`play()` 返回后，状态不一定已经是 `Playing`。调用方必须等待 `onStateChanged`
事件，不得假设操作立即生效。这条约束直接对应 libVLC 的异步线程模型，也是避免
界面状态竞争的基础。

### 3.2 接口职责

| 方法 | 语义 | 是否同步 |
|---|---|---|
| `open(item)` | 请求打开媒体 | 异步 |
| `play()` | 请求开始或继续播放 | 异步 |
| `pause()` | 请求暂停 | 异步 |
| `stop()` | 请求停止并归零 | 异步 |
| `seek(pos)` | 请求定位 | 异步 |
| `setVolume(v)` | 设置音量 0 至 100 | 同步 |
| `setMuted(b)` | 设置静音 | 同步 |
| `setVideoSurface(handle)` | 设置视频输出目标 | 同步 |
| `state()` | 读取当前状态快照 | 同步 |
| `position()` | 读取当前位置快照 | 同步 |
| `duration()` | 读取可能未知的总时长快照 | 同步 |
| `isSeekable()` | 读取是否可定位的快照 | 同步 |
| `setEventListener(l)` | 注册事件监听器 | 同步 |

快照类方法可能从任意线程调用，实现必须自行保证线程安全。

### 3.3 事件监听接口

```text
PlayerEventListener
├── onStateChanged(PlaybackState)
├── onPositionChanged(PlaybackPosition)
├── onDurationChanged(std::optional<milliseconds>)
├── onEndReached()
└── onError(PlaybackError)
```

**关键约定**：这些回调可能在内核线程上被调用。接口注释必须明确写出这一点，
实现者不得假设自己在主线程。阶段 4 将回调固定为 `noexcept`；监听器不得让异常
越过 C 回调边界，也不得在回调中同步调用停止、释放或更换监听器。

### 3.4 假内核

`FakePlayerEngine` 在阶段 3 与接口同时诞生，作用有三个：

1. 让状态机和播放列表测试脱离 libVLC。
2. 让 GUI 测试脱离真实播放能力。
3. **提前证明接口可替换**。如果假内核难以实现，说明接口设计泄漏了 libVLC 的
   实现细节，必须在阶段 3 修正，不能把问题带入后续阶段。

假内核由测试直接驱动：测试调用 `emitStateChanged(...)` 主动触发事件，从而精确
控制时序，不依赖真实播放的不确定性。

## 4. VlcPlayerEngine 实现要点

### 4.1 初始化参数

创建 libVLC 实例时传入的参数集中在一个函数中定义，不散落。第一版需要的参数
类别：

| 类别 | 目的 |
|---|---|
| 界面禁用 | 不让 libVLC 创建自己的界面 |
| 日志级别 | 控制内核输出的详细程度 |
| 音频输出 | 测试环境下切换为哑输出 |
| 视频输出 | 测试环境下切换为哑输出 |

测试用的哑输出参数由构造参数控制，不是编译期宏。这样同一份代码既能真实播放，
也能在无声卡环境下跑集成测试。

### 4.2 句柄包装

libVLC 涉及三类句柄：实例、媒体对象、播放器对象。每一类都用带自定义删除器的
`std::unique_ptr` 包装，定义在 `src/engine_vlc/` 的私有头文件中。

业务代码中不出现任何显式的释放调用。

### 4.3 释放顺序

这是最容易出错的地方。规定的释放顺序：

```text
1. 解除事件监听（先断开回调，避免释放过程中仍有事件到达）
2. 请求播放器停止
3. 等待播放器进入终止状态
4. 释放播放器对象
5. 释放媒体对象
6. 释放实例
```

第 1 步必须在最前面。如果先停止再解除监听，停止过程中产生的事件可能访问已经
开始析构的对象。

第 3 步不能省略。直接释放正在播放的播放器对象会导致内核线程访问已释放内存。

实现时这段顺序必须有注释说明每一步的理由。

### 4.4 事件映射

libVLC 的事件与项目状态不是一一对应，需要映射表。映射规则集中在一个函数中，
不散落在多个回调里。

映射函数是纯逻辑，可以脱离 libVLC 单独测试：给定内核事件类型，返回项目状态。

### 4.5 位置事件节流

libVLC 的位置变化事件触发频率很高。节流在**内核实现层**完成，不在界面层：

- 位置事件最多约每 200 ms 向上层发送一次。
- 状态变化事件、时长确定事件、结束事件和错误事件**永不节流**。
- 用户主动定位后立即发送一次，不等节流窗口。

在内核层节流的理由：这是内核特性造成的问题，应该在产生问题的那一层解决，
否则 libVLC 的事件频率细节会泄漏到界面层并被重复处理。

## 5. 线程模型

### 5.1 线程清单

v0.1 只有两类线程需要项目自己关心：

| 线程 | 由谁创建 | 职责 |
|---|---|---|
| GUI 主线程 | Qt | 所有控件操作、状态机、播放列表 |
| libVLC 内部线程 | libVLC | 解码、渲染、事件回调 |

项目自己不创建任何线程。这是选择 libVLC 的直接好处。

### 5.2 事件跨线程投递

```text
libVLC 事件线程
      │
      │ 调用 VlcPlayerEngine 注册的 C 回调
      ▼
VlcPlayerEngine 内部回调
      │
      │ 转换为项目事件，调用 PlayerEventListener
      ▼
EngineEventBridge（实现 PlayerEventListener，位于 GUI 层）
      │
      │ ★ 线程切换点：投递到 GUI 主线程
      ▼
GUI 主线程
      │
      ▼
PlayerPresenter 更新状态机并刷新控件
```

`EngineEventBridge` 是整个项目唯一的线程切换点。它的实现方式是 Qt 的队列连接：
在内核线程上发出信号，接收槽在主线程上执行。

**约束**：

- `EngineEventBridge` 的回调方法中，除了发出信号以外不做任何事。
- 不在其中访问控件、不加锁、不调用内核接口。
- 通过信号传递的必须是值类型，不能是指针或引用。
- 自定义类型作为信号参数前必须先注册到 Qt 的元类型系统。

### 5.3 禁止的操作

以下三条来自播放器开发中最常见的崩溃原因，写入
[代码规范.md](代码规范.md) 第 10 节强制执行：

1. 在内核事件回调中直接操作 Qt 控件。
2. 在内核事件回调中调用停止或释放这类会等待内核线程的接口。
3. 在内核事件回调中触发会同步等待主线程的操作。

第 2 条的典型场景：收到“播放结束”事件后想立刻切换下一首。正确做法是把事件
投递到主线程，由主线程发起切换。直接在回调里操作会造成死锁。

### 5.4 关闭流程

```text
用户关闭窗口
  → 主窗口拦截关闭事件
  → 通知 EngineEventBridge 停止转发（后续事件直接丢弃）
  → 请求内核停止
  → 等待内核释放完成
  → 释放内核对象
  → 允许窗口关闭
```

第二步很重要：进入关闭流程后，界面对象即将销毁，此时到达的事件不应再被处理。

阶段 11 专项验收“播放中关闭窗口，进程干净退出，无残留”。

## 6. GUI 层设计

### 6.1 职责划分

| 类 | 职责 | 不负责 |
|---|---|---|
| `MainWindow` | 控件布局、接收用户输入、显示状态 | 判断操作是否合法 |
| `PlayerPresenter` | 状态机驱动、决定控件启用状态 | 直接调用 libVLC |
| `EngineEventBridge` | 线程切换 | 任何业务逻辑 |
| `VideoOutputWidget` | 提供原生窗口句柄、处理尺寸 | 渲染内容 |
| `PlaylistModel` | 只读展示播放列表 | 修改播放顺序 |

`PlayerPresenter` 是控件状态的唯一来源。控件不各自维护 `isPlaying` 之类的
布尔值，全部从展示逻辑读取。

### 6.2 控件启用规则

按状态决定，集中在一处：

| 状态 | 播放 | 暂停 | 停止 | 进度条 | 上/下一首 |
|---|---|---|---|---|---|
| 空闲 | 禁用 | 禁用 | 禁用 | 禁用 | 按列表 |
| 打开中 | 禁用 | 禁用 | 启用 | 禁用 | 按列表 |
| 播放中 | 禁用 | 启用 | 启用 | 按可定位 | 按列表 |
| 已暂停 | 启用 | 禁用 | 启用 | 按可定位 | 按列表 |
| 已停止 | 启用 | 禁用 | 禁用 | 禁用 | 按列表 |
| 播放结束 | 启用 | 禁用 | 禁用 | 禁用 | 按列表 |
| 播放失败 | 禁用 | 禁用 | 禁用 | 禁用 | 按列表 |

这张表直接对应 GUI 测试用例，实现和测试都以它为准。

### 6.3 视频输出

第一版采用最简单可靠的方案：把一个 Qt 控件的原生窗口句柄交给 libVLC，由内核
直接向该窗口绘制。

注意事项：

- 该控件必须启用原生窗口属性，否则拿不到有效句柄。
- 该控件上不叠加子控件，也不使用半透明效果，否则可能被内核绘制覆盖。
- 句柄必须在控件真正创建后才获取，不能在构造函数中获取。
- 切换媒体时需要清理上一段画面，避免残留最后一帧。
- 窗口尺寸变化由内核自行处理，项目只负责保持宽高比设置。

自定义渲染回调方案更灵活，但需要自己处理像素格式和绘制，不纳入当前已封存的版本
路线；如将来确有需求，必须重新建立独立规划。

### 6.4 进度条交互

拖动进度条时有一个常见问题：内核的位置事件会不断把滑块拉回去。处理方式：

- 用户按下滑块时，暂停接受内核位置更新。
- 拖动期间只更新时间文字，不改变播放位置。
- 用户松开滑块时，发起一次定位请求，并恢复接受位置更新。

这一行为在阶段 7 单独测试。

## 7. 播放列表

### 7.1 职责

`Playlist` 是纯 C++ 类型，位于核心层，不依赖 Qt。负责：

- 保存媒体项序列和当前索引。
- 根据播放模式计算下一项和上一项。
- 处理边界情况：空列表、单项列表、末尾项。

`PlaylistModel` 是 Qt 只读视图模型，持有对 `Playlist` 的引用，不复制业务对象。

### 7.2 播放模式行为

| 模式 | 当前项结束后 | 手动“下一首”在末尾时 |
|---|---|---|
| 顺序播放 | 末尾项结束后停止 | 无动作 |
| 列表循环 | 末尾项结束后回到首项 | 回到首项 |
| 单曲循环 | 重播当前项 | 切换到下一项 |

单曲循环下手动切换仍然前进，这是有意设计：自动行为和手动行为可以不同。这条
容易被误解，实现时必须有注释说明。

## 8. 错误处理

### 8.1 映射流程

```text
libVLC 报告错误
  → VlcPlayerEngine 提取原始信息
  → 映射为 PlaybackErrorKind
  → 生成中文 userMessage
  → 通过 onError 事件上报
  → 投递到主线程
  → PlayerPresenter 进入失败状态
  → MainWindow 显示提示
```

### 8.2 映射规则

libVLC 提供的错误信息有限，很多情况只能给出笼统结果。因此映射不完全依赖内核
返回值，也结合项目自己的前置检查：

| 判断依据 | 结果类别 |
|---|---|
| 本地文件路径不存在（打开前检查） | `SourceNotFound` |
| 本地文件存在但无法读取（打开前检查） | `SourceUnreadable` |
| 内核报告错误，且文件可读 | `UnsupportedFormat` |
| 内核初始化失败 | `EngineNotInitialized` |
| 其余情况 | `Unknown` |

在调用内核之前先做本地文件检查，能把最常见的两类失败区分出来，给用户更有用的
提示。这是有意增加的一步，不是多余检查。

### 8.3 失败后的可恢复性

单项失败不影响整体：

- 列表中其他项仍可正常播放。
- 用户可以手动切换到其他项。
- 顺序播放模式下，自动切换遇到失败项时跳过并继续，连续失败超过列表长度则停止。

最后一条防止全列表失败时陷入无限循环，实现时必须有计数上限。

## 9. 日志（阶段 9）

沿用与 BatchGuard 相同的思路：

- 单行 UTF-8 结构化格式：时间、级别、所属层、摘要、附加字段。
- 只输出到终端，不写文件。
- **不记录媒体文件的完整路径**，只记录文件名或脱敏后的标识。
- 核心层不依赖日志设施，日志记录由应用层建立。

记录的关键节点：程序启动与内核初始化、媒体打开请求与结果、状态转换、定位请求、
播放失败、程序退出与内核释放。

## 10. 验证方式

| 设计点 | 验证手段 | 阶段 |
|---|---|---|
| 接口可替换 | 假内核能完整实现接口 | 3 |
| 状态机正确 | 纯 C++ 单元测试，覆盖合法与非法转换 | 3 |
| 内核链路可用 | 真实 libVLC 集成测试，哑输出 | 4 |
| 资源释放正确 | 反复创建释放内核，检查无泄漏无残留线程 | 4 |
| 线程边界正确 | 内核线程发事件，断言处理发生在主线程 | 5 |
| 控件状态正确 | 按第 6.2 节表格逐状态验证 | 5 |
| 视频输出正确 | 人工验收，无法自动化 | 6、11 |

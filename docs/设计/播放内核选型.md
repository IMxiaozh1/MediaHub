# MediaHub 播放内核选型

> 状态：已决策、已实施并随 v0.2 封存。
>
> 决策日期：2026-08-03。
>
> 分类：设计。
> 本文档记录播放内核的候选方案、比较过程、最终选择和抽象边界。
> 这是本项目最核心的技术决策，后续所有分层都建立在它之上。

## 1. 要解决的问题

播放器分成两层：

```text
界面层：窗口、按钮、进度条、播放列表        ← 无论选哪种内核都要自己写
    ↓ 调用
内核层：打开媒体、解码、输出声音、输出画面  ← 本文档决定这一层由谁实现
```

界面层的工作量是固定的。真正的分歧在于选择 Qt 自带的多媒体能力，还是接入
专门的播放内核。

## 2. 候选方案

### 2.1 方案 A：Qt Multimedia

使用 Qt 5.14 自带的 `QMediaPlayer` 和 `QVideoWidget`。

```text
Qt Widgets 界面
    ↓
QMediaPlayer + QVideoWidget
    ↓
Windows DirectShow / Media Foundation
```

| 维度 | 评价 |
|---|---|
| 额外依赖 | 无。本机 Qt 套件已包含 `Qt5Multimedia` |
| 本地播放 | 常见 MP3、MP4 可用 |
| 直播支持 | 不可用。HLS、RTMP、FLV 等直播格式基本不支持 |
| 开发量 | 最小 |
| 可学习性 | 低。内核完全是系统组件 |
| 部署 | 最简单，只需 Qt 运行库 |

**否决原因**：项目的核心动机之一是“给一个地址就能看直播”。Qt Multimedia 在
Windows 上依赖系统解码组件，直播协议支持缺失，第二版会直接卡死。选它等于在
第一版就把第二版的路堵上。

### 2.2 方案 B：libVLC

把 VLC 播放器的内核以库的形式嵌入自己的程序。

```text
Qt Widgets 界面
    ↓
自己封装的 PlayerEngine 接口
    ↓
libVLC（解封装 + 解码 + 音频输出 + 视频渲染）
```

| 维度 | 评价 |
|---|---|
| 额外依赖 | libVLC SDK，约 40 MB；运行时含插件约 130 MB |
| 本地播放 | 覆盖面很广，几乎不需要额外处理 |
| 直播支持 | HLS、RTMP、RTSP、FLV、UDP 等直接可用 |
| 开发量 | 小。一个地址交给它就能播 |
| 可学习性 | 中。能学到接口设计、线程边界和资源管理，学不到解码细节 |
| 部署 | 需要携带两个 DLL 和整个插件目录 |
| 许可证 | 内核 LGPLv2.1+，部分插件 GPLv2+，需要单独复核 |

## 3. 最终决策

**采用方案 B：以 libVLC 作为 MediaHub 的播放内核，并用 `PlayerEngine` 抽象接口
隔离界面、核心逻辑和第三方回调。**

```text
v0.1  界面 → PlayerEngine 接口 → VlcPlayerEngine    → libVLC
v0.2  界面 → PlayerEngine 接口 → VlcPlayerEngine    → libVLC（增加网络流处理）
```

### 3.1 选择理由

1. **第一版能尽早得到可用产品**。界面、状态机、播放列表、错误处理这些工作在
   任何方案下都要做，先用成熟内核把它们跑通，风险最低。
2. **直播协议覆盖满足目标**。HLS、RTMP、RTSP、FLV、UDP 等能力可以直接复用成熟
   实现，项目集中处理界面、状态、超时和取消语义。
3. **抽象接口保留测试价值**。核心和 GUI 测试使用假内核精确控制异步事件，不依赖
   真实音频设备、网络或 libVLC 时序。
4. **维护边界清晰**。libVLC 类型只存在于内核实现层，GUI 和核心公共接口不泄漏
   第三方类型。

### 3.2 付出的代价

- 需要多写一层抽象接口，v0.1 多出约十几个虚函数的样板代码。
- 交付包中要携带 libVLC 的插件目录，体积明显大于纯 Qt 方案。
- 需要处理 LGPL 与 GPL 混合的许可证复核。

这些代价是已知且可接受的。

## 4. 抽象接口设计原则

`PlayerEngine` 是本项目最重要的一条边界。它的设计要满足：能被 libVLC 实现，
也能被一个不做任何真实播放的假实现满足。

### 4.1 接口必须遵守的约束

- 不出现任何 Qt 类型。
- 不出现任何 libVLC 类型。
- 不出现 Windows 专属类型。视频输出句柄使用 `void*` 传递，含义由实现层解释。
- 时间统一使用 `std::chrono::milliseconds`，不用裸整数。
- 所有操作都是请求，不保证同步完成。真正的结果通过事件回传。

最后一条尤其重要：`play()` 的含义是“请求开始播放”，不是“播放已经开始”。真正
进入播放状态由事件通知。libVLC 通过内部线程异步工作，接口如果假设同步就会造成
状态竞争或界面阻塞。

### 4.2 接口大致形态

以下是设计意图示意，正式签名在阶段 3 确定：

```text
PlayerEngine
├── open(媒体项)            请求打开
├── play()                  请求播放
├── pause()                 请求暂停
├── stop()                  请求停止
├── seek(位置)              请求定位
├── setVolume(0..100)       设置音量
├── setMuted(bool)          设置静音
├── setVideoSurface(void*)  设置视频输出目标
├── state()                 当前状态快照
├── position()              当前位置快照
├── duration()              总时长，可能未知
├── isSeekable()            是否可定位
└── setEventListener(监听器) 注册事件回调

PlayerEventListener
├── onStateChanged(状态)
├── onPositionChanged(位置)
├── onDurationChanged(时长)
├── onEndReached()
└── onError(失败信息)
```

### 4.3 事件线程的关键约束

libVLC 的事件回调在 libVLC 自己的线程上触发，不是在 GUI 主线程。这带来两条
不可违反的规则：

1. **回调里不能直接操作 Qt 控件**。必须通过跨线程投递把事件送回主线程。
2. **回调里不能调用会等待内核线程的接口**。例如在事件回调中直接调用停止或
   释放，可能造成死锁。需要停止时，先投递到主线程，再由主线程发起。

这两条是播放器最常见的崩溃和卡死来源，会在
[第一版实现.md](第一版实现.md) 中给出具体的处理方式，并在阶段 5 单独验证。

## 5. libVLC 版本与获取

- 使用 VLC 3.0.x 系列的 Windows 64 位版本，与本机 MSVC 工具链匹配。
- 官方下载来源：VideoLAN 官方站点的 win64 发行包。
- 实际使用的确切版本号在阶段 1 确定后记录到
  [依赖接入与部署说明.md](../交付/依赖接入与部署说明.md) 和交接文档。

不使用 VLC 4.x 开发版本。4.x 的接口仍在变动，且部分函数语义与 3.x 不同。

### 5.1 为什么不放进 Third_Party

`Third_Party/` 只保存需要随仓库固定版本管理的源码。libVLC 的运行时包含两个
DLL 和一个包含数百个插件文件的目录，总体积超过 100 MB，不适合进入 Git。

采用与 Qt 相同的处理方式：作为开发机上的外部 SDK，通过 CMake 变量指向本地
解压目录。项目 CMake 中不硬编码任何本机绝对路径。

## 6. 许可证注意事项

需要在阶段 12 交付前完成复核，本节先记录已知事实：

- libVLC 核心库使用 LGPLv2.1 或更高版本。动态链接的情况下，调用方的代码不必
  开源，但必须允许用户替换该库，并提供许可证文本。
- VLC 官方发行包中的**部分插件使用 GPLv2 或更高版本**。如果分发包里包含这些
  插件，整个分发可能需要遵守 GPL 条款。
- 结论：自用和学习不受影响；如果将来要对外分发，必须逐个确认所携带插件的
  许可证，或裁剪掉 GPL 插件。

这一点不能等到交付前才发现，因此提前记录在选型文档中。

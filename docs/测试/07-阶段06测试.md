## 1. 实现边界

阶段 6 当前已完成以下实现：

- 建立 `VideoOutputWidget`，启用 Qt 原生窗口属性并只暴露不透明 `void*` 句柄。
- 原生句柄只在控件显示并真正创建后发布；句柄变化时会重新提交给播放内核。
- 视频控件没有覆盖在画面上的子控件，占位文字由控件自身在非视频状态绘制。
- 已知音频扩展名显示明确的音频占位，视频准备、停止、结束和失败各有独立占位。
- 切换媒体时先进入准备占位，立即覆盖上一段视频的最后一帧。
- 视频打开、缓冲、播放和暂停状态保持原生画面区域活动。
- 视频活动时 Qt 停止擦除和绘制原生画布，避免覆盖 libVLC 直接输出的帧。
- 控件提供 16:9 首选尺寸，并随主窗口布局一起缩放，不强制布局保持固定比例。
- F11、菜单或按钮进入纯画面全屏；全屏隐藏界面框架，Esc 或 F11 退出。
- 关闭窗口时先停止事件转发、解除监听、把视频句柄设为 `nullptr`，最后请求停止。

本阶段没有加入进度、音量、静音或播放列表。视频解码和宽高比由 libVLC 负责，
GUI 只维护可缩放的原生输出目标。

## 6. 实机失败诊断与修复

首次打开验收者桌面上的 MP4 时没有正常显示视频。诊断过程没有修改、复制或提交该
媒体文件，结论如下：

- 文件头是标准 `mp42/isom` MP4，同一套 VLC 3.0.21 识别出约 46 秒的 AAC 音轨和
  H.264 视频轨。
- VLC 的 AAC 与 H.264 解码器均成功启动，读取到结尾后以退出码 0 正常结束，排除
  文件损坏、容器无法解析和解码器缺失。
- GUI 在视频活动状态仍通过 `QPainter` 把整个原生画布填充为黑色，并声明
  `WA_OpaquePaintEvent`，该绘制路径可能覆盖 libVLC 直接写入窗口的帧。
- 修复后，视频活动状态启用 `WA_NoSystemBackground`、关闭
  `WA_OpaquePaintEvent`，且 `paintEvent` 不再执行任何 Qt 绘制；返回占位状态时恢复
  Qt 绘制并立即覆盖最后一帧。
- Qt 回归测试新增两种画布属性的双向断言；Debug 与 Release 全量测试均通过。
- 实机复验又发现 libVLC 在已经进入播放后仍可能发送 98% 或 100% 的迟到缓冲事件。
  原实现把界面状态降回 `Buffering`，造成视频已有画面但暂停按钮一直不可用。
- 新增 `isBufferingInProgress` 判断：缓冲达到 100%，或 libVLC 已处于 `Playing` 时忽略
  迟到事件；集成测试确认播放位置前进后状态仍保持 `Playing`。
- 去除视频控件的强制 16:9 高宽布局，调整默认窗口、最小尺寸和边距，确保常规窗口
  中打开及全屏按钮始终可见；16:9 仍作为首选尺寸交给布局参考。
- 程序支持 `MediaHub.exe <媒体路径>`，便于直接打开指定媒体完成可重复实机验证。

以上修复均在最终 Release 程序和验收媒体上完成复验。

## 8. 已知问题

- 音频与视频的界面模式当前按扩展名区分；未知音频扩展名会得到视频区域，但不影响
  内核实际解码。更精确的轨道识别可在后续扩展核心媒体信息时加入。
- 全屏继续只保留视频画面；阶段 7 的进度与音量面板随其他界面框架一起隐藏。
- 单一验收媒体不能代表所有编码组合；更多格式、显示器 DPI 和主观音画同步仍在阶段
  11 的集中验收范围内。

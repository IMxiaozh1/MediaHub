# MediaHub v0.7 长直播切换失效修复测试

> 日期：2026-08-17。
>
> 状态：源码修复、Debug 自动化与真实使用人工放行全部通过。

## 1. 问题与根因

用户反馈直播持续播放较长时间后，切换到其他直播源无法开始播放，随后打开本地音频或
视频也没有响应，只能退出并重新启动程序恢复。

内核原有方案允许旧直播播放器在后台停止，但把普通切换限制为最多 3 个并发回收任务，
为 Stop 预留第 4 个名额。libVLC 3 的轨道关闭或 `libvlc_media_player_stop()` 可能永久
等待；名额只在整个停止和释放完成后归还。因此多个旧会话长期不退出时，硬上限会永久
拒绝后续 `open()`，直播和本地媒体共用的打开入口都会失效。

直播切直播还会复用当前 libVLC 实例。长时间网络播放后的内部状态可能继续影响新建的
播放器，不利于把新直播会话与旧网络读取彻底隔离。

## 2. 修复策略

1. 每次从直播切换到任意新媒体时创建全新的 libVLC 实例；新直播和本地媒体都不复用
   旧直播实例。
2. 旧播放器先静音并保持绑定自己的隐藏视频子窗口，再交给后台回收，避免旧声音混入
   新媒体，也不让仍活动的 vout 访问已经销毁的 HWND。
3. 后台最多运行 4 个回收线程。超过并发数的旧播放器进入内部队列，不再用硬上限拒绝
   新的打开或停止请求。
4. 回收线程完成轨道关闭、Stop、播放器和实例释放后，才通知 GUI 销毁对应旧子窗口。
   即使 libVLC 的某个停止调用长期阻塞，唯一内核控制线程仍可继续处理新媒体。

## 3. 回归用例

| 编号 | 场景 | 结果 |
|---|---|---|
| LSR-A01 | 连续直播切换时统计 libVLC 实例 | 每次切换创建新实例，通过 |
| LSR-A02 | 4 个旧播放器的停止观察器全部阻塞 | 后台活跃回收线程最大值保持 4，通过 |
| LSR-A03 | 回收线程占满后继续打开第 6 个直播 | 500ms 内进入 Opening，无 EngineBusy，通过 |
| LSR-A04 | 回收线程占满后切换运行时生成的本地 WAV | 500ms 内进入 Opening，1 秒内进入 Playing，通过 |
| LSR-A05 | 上述状态下执行 Stop | 500ms 内进入 Stopped，通过 |
| LSR-A06 | 解除阻塞后清空排队任务 | 6 个旧会话均进入回收并退出，通过 |

修复前，LSR-A01 只观察到构造阶段的两个实例，LSR-A03 在第 4 个旧会话阻塞后无法再
进入 Opening；修复后两项均稳定通过。

## 5. 人工验收

自动化使用阻塞观察器模拟比真实长直播更坏的永久 Stop 阻塞，但真实音画输出、旧声音
是否立即消失和具体直播源的长期行为仍需人工确认：

| 编号 | 场景 | 状态 |
|---|---|---|
| LSR-M01 | 让原问题直播持续播放到容易复现的时长，再切换另一直播 | 通过，用户放行当前 Debug 候选 |
| LSR-M02 | 切换后旧直播声音立即停止，新直播音画正常 | 通过，用户放行当前 Debug 候选 |
| LSR-M03 | 随后切换本地音频和本地视频，均可正常播放 | 通过，用户放行当前 Debug 候选 |
| LSR-M04 | 全程无独立 VLC 窗口，Stop 和关闭程序正常 | 通过，用户放行当前 Debug 候选 |

用户在本轮启动的 Debug 候选上完成使用后明确要求提交，人工门禁解除。本轮只提交源码、
测试和文档，不更新 `dist/MediaHub-0.7.0-win64/`，正式发布目录仍保持原 v0.7 基线。

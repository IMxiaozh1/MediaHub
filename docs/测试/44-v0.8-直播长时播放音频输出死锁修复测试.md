# MediaHub v0.8 直播长时播放音频输出死锁修复测试

> 日期：2026-08-25。
>
> 状态：Debug/Release 自动化、正式包验证和用户真实音频/直播人工验收全部通过。

## 1. 问题与现场证据

用户反馈直播播放较长时间后画面卡住，随后刷新、双击当前频道或切换其他频道均无法播放。
现场正式程序 PID `31520` 的窗口仍可响应，但直播页一直显示“正在刷新直播…”，没有已建立的
网络连接，说明请求尚未进入新直播源的网络打开阶段。

在不结束现场进程的前提下抓取完整线程转储。唯一内核控制线程阻塞在以下调用链：

```text
ntdll!RtlSleepConditionVariableCS
libmmdevice_plugin
libvlccore!vlc_module_load
libvlccore!module_need
libvlccore!input_resource_GetAout
libvlc!libvlc_media_player_new
MediaHub!VlcPlayerEngine::Impl::replacePrimaryPlayer
```

对应源码位置是替换主播放器时的 `libvlc_media_player_new()`。libVLC 3.0.21 创建播放器会同步
初始化音频输出；Windows `mmdevice` 插件在现场永久等待后，所有刷新、切台和停止命令都堵在
同一个控制队列后。因此界面仍能响应，但任何直播都无法继续播放。

现场诊断材料保存在本机临时目录，不进入仓库：

- `MediaHub-hang-31520-20260825-093210.dmp`；
- `MediaHub-hang-31520-dbgeng.txt`；
- `MediaHub-hang-31520-stacks.txt`。

## 2. 修复策略

1. Windows 正式播放实例显式传入 `--aout=directsound`，绕过已在现场证实死锁的默认
   `mmdevice` 后端。
2. 波形分析实例始终传入 `--aout=dummy`。分析播放器通过 PCM 回调取样，不应初始化或占用
   真实音频设备。
3. 网络播放器替换时继续创建全新 libVLC 实例，但每个新实例都沿用上述正式播放参数。
4. 不调用 `libvlc_audio_output_set()` 动态切换后端；该接口会同步重建音频输出，仍可能在
   唯一控制线程中等待。
5. 保留既有命令队列、独立视频句柄和后台旧播放器回收策略，本轮不扩大为异步播放器工厂
   重构。

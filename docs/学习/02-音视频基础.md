> 系统学习音视频技术。项目使用现成内核，这些概念中的大部分只需要“知道它存在”；
> 本文不对应后续版本排期。

## 1. 一个媒体文件里到底有什么

打开一个 `.mp4` 文件，里面不是"视频"，而是一个**容器**，容器里装着若干条
**流**：

```text
example.mp4  ← 容器（Container）
├── 视频流   用某种视频编码压缩的画面数据
├── 音频流   用某种音频编码压缩的声音数据
├── 字幕流   （可选）
└── 元数据   时长、分辨率、标题等
```

所以描述一个媒体文件需要两个层面的信息：

- **容器格式**：数据怎样组织和封装。常见的有 MP4、MKV、AVI、MOV、FLV、TS。
- **编码格式**：每条流用什么算法压缩。视频常见 H.264、H.265、VP9；音频常见
  AAC、MP3、FLAC、Opus。

**这解释了一个常见困惑**：为什么两个都是 `.mp4` 的文件，一个能播一个不能？
因为扩展名只说明容器，不说明里面用了什么编码。播放器支持 MP4 容器，不等于
支持里面的所有编码。

这也是为什么 [03-v0.1-第一版MVP.md](../规划/03-v0.1-第一版MVP.md) 说"按内核能播就播的原则
处理，不维护自己的白名单"——项目无法预先知道一个文件能不能播，只能试。

## 2. 播放一个文件要经过哪些步骤

```text
读取文件字节
    ↓
解封装（Demux）        从容器中把各条流分离出来
    ↓
    ├── 视频数据包 ──→ 视频解码 ──→ 一帧一帧的图像 ──→ 显示
    └── 音频数据包 ──→ 音频解码 ──→ 一段一段的采样 ──→ 播放
                                        ↑
                                   两者需要对齐
```

每一步都有可能失败，失败原因也不同：

| 步骤 | 典型失败 | 对应的错误类别 |
|---|---|---|
| 读取文件 | 文件不存在、没有权限 | `SourceNotFound` / `SourceUnreadable` |
| 解封装 | 不是媒体文件、文件损坏 | `UnsupportedFormat` |
| 解码 | 编码格式不支持、缺少解码器 | `UnsupportedFormat` |
| 输出 | 没有音频设备 | `AudioDeviceUnavailable` |

这张表对应 [02-v0.1-实现设计.md](../设计/02-v0.1-实现设计.md) 第 2.4 节的失败分类。

MediaHub 中，解封装和解码全部由 libVLC 完成，项目只处理最前面的文件检查和最后的
错误分类；当前版本路线不自行实现中间两步。

## 3. 时间是怎么表达的

播放器里的时间有几个容易混淆的概念：

| 概念 | 含义 |
|---|---|
| 时长（Duration） | 媒体总共多长 |
| 位置（Position） | 当前播放到哪里 |
| 时间戳（Timestamp） | 某一帧应该在什么时刻呈现 |
| 时间基（Time base） | 时间戳的单位，不同流可能不同 |

v0.1 只需要用到前两个，而且都由内核提供，项目直接用毫秒表达即可。

**时间基**主要由播放内核处理：不同流的时间戳可能用不同的单位计数，必须换算到
统一尺度才能比较。MediaHub 当前只需要知道它存在。

**关于时长未知**：直播流没有总时长。这就是为什么
[02-v0.1-实现设计.md](../设计/02-v0.1-实现设计.md) 里 `total` 用 `std::optional` 而不是
用 `0` 或 `-1` 表示——用特殊数值表达"没有"，迟早会有人忘记检查。

## 4. 音视频同步是什么问题

声音和画面是分别解码的，解码速度也不一样。如果各自解码完就立刻输出，很快就会
对不上——这就是"音画不同步"。

解决办法是选一个**时钟**作为基准，让另一方跟着它走：

- 以音频为基准（最常用）：声音连续播放，视频帧根据音频进度决定显示、等待还是
  丢弃。
- 以视频为基准：适合无音频的场景。
- 以外部时钟为基准：适合多路同步。

为什么通常以音频为准？因为人耳对声音的断续和变速非常敏感，而眼睛对偶尔丢一帧
基本无感。让视频迁就音频，代价最小。

**MediaHub 不直接处理这个问题**，libVLC 内部已经做好了。这也是使用成熟播放内核
的主要价值之一。

## 5. 定位为什么不精确

拖动进度条跳到某个时间点，实际到达的位置往往不完全一致。原因在于视频编码的
帧间压缩：

- 有些帧是完整的图像，可以独立解码（关键帧）。
- 大多数帧只记录与前后帧的差异，必须依赖其他帧才能解码。

跳转只能落在关键帧上，否则解码器没有参考数据，画面会花。而关键帧之间可能相隔
几秒。

所以：

- 定位精度受限于关键帧间隔，这是编码特性，不是程序缺陷。
- [03-v0.1-第一版MVP.md](../规划/03-v0.1-第一版MVP.md) 的验收标准写的是"跳转到目标位置附近"，
  不是"精确到毫秒"，就是这个原因。
- 有些媒体完全不可定位（比如某些直播流），所以接口里有 `isSeekable()`。

## 6. 网络流协议（v0.2 相关）

直播和点播的区别不只是"在不在本地"：

| 特性 | 本地文件 | 点播（网络） | 直播 |
|---|---|---|---|
| 总时长 | 已知 | 已知 | 未知 |
| 可定位 | 是 | 通常可以 | 通常不可以 |
| 数据来源 | 磁盘 | 服务器，可随机读取 | 持续推送的流 |
| 中断可能 | 极少 | 网络波动 | 网络波动 + 主播下播 |
| 打开耗时 | 很短 | 取决于网络 | 取决于网络 |

常见的直播传输方式有基于 HTTP 的分片协议（如 HLS，地址通常以 `.m3u8` 结尾）、
实时消息协议（RTMP）、实时流协议（RTSP）等。它们的共同点是数据边传边播，而不是
先下载完整文件。

**这解释了为什么 Qt 自带的播放能力不够用**：它依赖 Windows 系统解码组件，对这
些协议支持有限。而 libVLC 把这些协议都实现了，给一个地址就能处理。

v0.2 需要在这些概念上做的工作，主要不是"支持协议"（libVLC 已经支持），而是
处理**不确定性**：打开可能很慢、中途可能断、时长可能没有、可能不能定位。这些
都是界面和状态机要应对的问题。

## 7. 缓冲是怎么回事

网络播放时，数据到达速度不稳定。播放器会先攒一段数据再开始播，这段数据就是
缓冲区。

- 缓冲太小：网络稍有波动就卡顿。
- 缓冲太大：打开时等待时间长，直播延迟高。

这就是为什么播放状态里有 `Buffering` 这一项。本地播放几乎看不到这个状态，但

## 8. 视频画面是怎么显示出来的

解码后的一帧图像不是直接可显示的位图，它通常采用一种把亮度和色彩分开存储的
格式（常见的是 YUV 系列），需要转换后才能交给显示系统。

显示画面有两种常见做法：

| 做法 | 说明 | 本项目 |
|---|---|---|
| 交给内核直接画 | 把一个窗口句柄给内核，它自己完成转换和绘制 | v0.1 采用 |
| 自己拿到帧再画 | 内核通过回调交出每一帧，自己转换并绘制 | 当前路线不采用 |

第一种最简单可靠，但灵活性低（比如不方便在画面上叠加东西）。第二种灵活但要
自己处理格式转换和绘制性能。

v0.1 选第一种，理由见 [02-v0.1-实现设计.md](../设计/02-v0.1-实现设计.md) 第 6.3 节。

## 9. 术语速查

| 术语 | 一句话解释 |
|---|---|
| 容器 | 装载各条流的文件格式，如 MP4、MKV |
| 编码 | 压缩流数据的算法，如 H.264、AAC |
| 解封装 | 从容器中分离出各条流 |
| 解码 | 把压缩数据还原为图像或声音 |
| 流 | 容器中的一条独立数据轨道 |
| 帧 | 视频的一幅画面 |
| 关键帧 | 可以独立解码的完整帧，定位的落点 |
| 采样 | 音频的最小数据单位 |
| 时间戳 | 某份数据应该在何时呈现 |
| 时间基 | 时间戳的计量单位 |
| 缓冲 | 提前攒下的数据，用于抵抗速率波动 |
| 音视频同步 | 让声音和画面在时间上对齐 |
| 重采样 | 转换音频的采样率或声道数以匹配输出设备 |
| 硬件加速 | 用显卡而非 CPU 完成解码 |
